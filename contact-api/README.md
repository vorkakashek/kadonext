# Форма KADO: голосовые сообщения и SMTP

Сайт остаётся статическим. Отправку выполняет отдельный небольшой Node.js-обработчик:

```text
браузер → POST /api/contact → проверка аудио → MP3-вложения → SMTP → hello@kadonext.com
```

## Что уже работает

- Текст, голос или оба варианта в одной заявке.
- До двух записей общей длительностью 1 минута 30 секунд.
- Прослушивание и перемотка, удаление. Сообщения отправляются в порядке записи. Если браузер не воспроизводит аудио, доступна ссылка для скачивания.
- Запись запускается иконкой микрофона в поле описания проекта. Выбор устройства всегда доступен под полем справа; во время записи он заблокирован.
- Готовое сообщение сохраняется автоматически и входит в заявку. В карточке доступны прослушивание, перезапись и удаление.
- Перезапись сохраняет предыдущую версию до успешного завершения новой записи. Отмена или ошибка оставляет старую версию; успешная замена сохраняет место сообщения в порядке отправки.
- Индикатор уровня микрофона, предупреждения о тишине и слабом сигнале после десяти секунд. Это оценка сигнала, а не распознавание речи.
- Выбор доступного микрофона после предоставления разрешения.
- При сворачивании страницы запись останавливается; корректная записанная часть сохраняется автоматически.
- Серверная проверка количества, размера, контейнера и фактической длительности, преобразование в MP3.
- SMTP через TLS, фиксированный получатель, ограничение частоты, honeypot, ограничение параллельной обработки.

Записи находятся в памяти браузера и сохраняются при переключении компонентов формы и SPA-навигации. Перезагрузка страницы удаляет их. Проверка громкости не отправляет звук на сервер. Временные серверные файлы удаляются после обработки, в том числе при ошибке.

## Подключение отправки

1. Создать `.env` по образцу [../.env.example](../.env.example).
2. Заполнить `CONTACT_SMTP_HOST`, `CONTACT_SMTP_PORT`, `CONTACT_SMTP_USER`, `CONTACT_SMTP_PASS`, `CONTACT_MAIL_FROM`. Обычно нужен пароль приложения почтового ящика. Для порта 465 используется TLS сразу, для 587 — обязательный STARTTLS.
3. Установить FFmpeg и ffprobe на хост обработчика. Они должны быть в `PATH`; иначе задать `CONTACT_FFMPEG_PATH` и `CONTACT_FFPROBE_PATH`. Нужна сборка с `libmp3lame`.
4. Настроить `CONTACT_ALLOWED_ORIGINS` — точные адреса сайта, через запятую. Для LAN и HTTPS-туннеля добавить их адреса при проверке.
5. На production-хосте установить `NODE_ENV=production`, затем выполнить `npm ci --omit=dev` и `npm run contact:serve`. Требуется Node.js 24+.

Секреты SMTP не входят в Nuxt public runtime config, сборку браузера или git. `.env` уже исключён из git. Обработчик не логирует поля заявки и аудио.

### Разработка

`npm run dev` обслуживает `/api/contact` через тонкий Nuxt-адаптер. SMTP-параметры читаются из `.env` на сервере. После изменения `.env` потребуется перезапуск dev-сервера самим разработчиком; существующий сервер автоматически не перезапускается.

Локальная запись работает на `localhost`. Для телефона нужен HTTPS-туннель, поскольку обычный LAN HTTP не предоставляет доступ к микрофону. Политика Permissions-Policy хоста не должна запрещать `microphone` для собственного origin.

### Статический production-хост

`npm run build` выпускает `.output/public`. Nuxt API в эту статическую поставку не входит. На хосте направить `/api/contact` в отдельный процесс `contact-api/server.mjs`, например:

```nginx
location = /api/contact {
    client_max_body_size 13m;
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 120s;
}
```

При такой конфигурации можно установить `CONTACT_TRUST_PROXY=true`: прокси обязан перезаписывать `X-Forwarded-For`, а API-процесс не должен быть доступен напрямую. Если API размещён на другом хосте, перед сборкой задать `NUXT_PUBLIC_CONTACT_ENDPOINT=https://api.example.com/api/contact` и разрешить origin сайта в `CONTACT_ALLOWED_ORIGINS`.

Голосовые и текст отправляются только после нажатия кнопки и согласия пользователя. Сообщение об успехе появляется после принятия письма SMTP-сервером — это не гарантия попадания во входящие. Без SMTP-параметров обработчик возвращает понятную ошибку, сохраняет клиентский черновик и предлагает прямой email. Для публичной формы правила rate limit действуют в рамках одного процесса; при масштабировании нужна общая защита на прокси или в общем хранилище.

## Согласие на обработку данных

Форма содержит одну обязательную галочку согласия со ссылкой на `/consent`.
Политика `/privacy` доступна отдельной ссылкой и не требует второй галочки.
Текст согласия и его версия хранятся в `contact-api/consent.mjs`: этот источник
используют страница документа и серверный обработчик. При изменении текста
нужно обновить `CONTACT_CONSENT_VERSION` и одновременно выпустить сайт и API.
Заявки без текущей версии согласия отклоняются до отправки SMTP. Вместе с
заявкой письмо сохраняет дату отправки, версию, формулировку галочки и текст
согласия. Эти сведения нужно хранить вместе с соответствующим обращением.

## Проверка

```sh
npm run contact:test
npm run typecheck
npm run build
```

Тесты проверяют лимиты, замену, порядок, очистку ресурсов, гонку разрешения микрофона, предупреждения, валидацию заявки, ошибки SMTP и преобразование реальных WebM/MP4/Ogg в MP3. Для тестов нужны FFmpeg и ffprobe. Письма в тестах не отправляются внешним получателям.

Перед публикацией отдельно проверить на настоящих iPhone/Safari и Android/Chrome: разрешение и отказ, отключение гарнитуры, тишину, тихую речь, возврат из фона, воспроизведение, лимит и реальную доставку письма через выбранный SMTP. ФИО и контактная почта оператора заполнены в `/privacy` и `/consent`; размещение обработчика и почты, договорные условия провайдеров и уведомление Роскомнадзора требуют отдельной проверки.
